# 内容与设计契约

基线：2026-11-12，仓库 `pagipdoc/pagsmile-bank-developer-docs`，现有站点设计与 Sandbox 调试方式。以下“必须”是维护要求，不代表校验工具能够自动证明每条都正确。已确认的业务变化可以修订契约，但必须同步说明依据、影响和验证结果。

## C01 — 事实必须可追溯

每个新增或变化的 method、path、字段、类型、必填性、默认值、枚举、限额、错误、状态和示例，都必须能追溯到适用版本的已审核公开契约、负责人确认或源码与测试证据。Sandbox 实测作为补充证据记录日期与环境。

有冲突先列出冲突；未知不填行业惯例，不挪用其他支付公司的数值。文档可以解释接口，但不能替接口定义尚不存在的行为。

## C02 — 一个协议，两种语言

| 内容 | 所在位置 | 必须保持 |
| --- | --- | --- |
| 英文协议 | `openapi/en.json` | 与批准的公开契约一致 |
| 葡语协议 | `openapi/pt-br.json` | 与英文协议结构相同，仅翻译描述文字 |
| 英文页面 | 根目录、`api-reference/` | 使用英文 spec 和英文内链 |
| 葡语页面 | `pt-br/` | 相同相对路径，使用葡语 spec 和 `/pt-br/` 内链 |
| 导航语言标识 | `docs.json` | `en`、`pt-BR` |
| 组件语言参数 | 现有 React snippets | 英文默认 `en`，葡语 `lang="pt"` |

字段名、枚举、`operationId`、凭证名称、JSON 键和代码中的协议值不得翻译。金额类型、精度、默认值与边界也不得因翻译变化。描述、代码注释和示例的业务含义需要人工核对，结构检查不能替代翻译审阅。

## C03 — 入口与信息结构

保留 Guides / API reference 两类入口和现有产品分组。一个操作在每种语言中有一个主要参考页；改名或迁移时使用 `docs.json.redirects` 保留旧地址。不要删除旧链接后只补一个新页面。

`docs.json` 是导航和重定向的生效文件。根目录 `redirects.json` 是被 `.mintignore` 排除的旧材料，不是发布配置。

注册说明中 Banking portal registration 必须先于 Business onboarding registration。API access 页面负责凭证与 IP 配置；其他页面链接到它，不复制一套容易漂移的配置说明。

## C04 — Sandbox 是在线工具的唯一目标

| 入口 | 允许的行为 |
| --- | --- |
| Banking platform 导航 | 打开生产 Banking 平台；不改变为独立 Sandbox 登录入口 |
| 首页起步任务 | 引导到 Sandbox 快速开始 |
| Developer Center | 按当前产品流程使用 Sandbox 测试账户与测试凭证 |
| 文档中的 AK/SK 输入、签名和在线发送 | 仅接受和使用 Sandbox 凭证与地址 |
| Production API 地址 | 作为参考文字显示；不加入可执行 Playground 的服务器列表 |

现有 Sandbox base URL 为 `https://ebanking-openapi-sandbox.pagsmile.com.br`。Production 参考地址为 `https://ebanking-openapi.pagsmile.com.br`。两份 OpenAPI 的 `servers`，以及 path/operation 上的覆盖配置，都不能把在线请求指向 Production。`docs.json.api.playground.proxy` 保持 `false`；改变请求经过的位置会改变 IP 白名单行为，必须另行验证。

开发者中心测试和文档浏览器测试使用当前电脑的公网出口 IP；服务端调用使用服务器出口 IP。公司网络或 VPN 下以实际出口为准。不能把内网地址作为公网白名单地址，也不能把浏览器测试成功当成服务器已可访问。

## C05 — 认证、签名与凭证范围

每个操作分别确认 ACCOUNT、USER、PLATFORM 的允许范围，以及 `X-ISPB`、`X-Account-Number` 的要求。不能因为相邻页面使用某种凭证就照搬。

签名中的 method、path、headers 和 body 必须与发送请求一致，签名后不再改写 JSON。每次尝试生成新的 nonce、timestamp 和签名；重试是否可执行仍取决于该操作的幂等与状态契约。

现有 `PlaygroundSigner` 的 `scope` 含义：`account` 用于需要账户上下文的操作；`user` 仅使用 USER 且不附账户选择头；`owner` 使用 USER 或 ACCOUNT 且不附账户选择头。是否允许具体凭证仍以该操作已确认的契约为准。

当前工具的发送分支固定使用 POST，且路径输入有限制；新接口超出现有支持时必须先适配。浏览器对账户选择头的 CORS 限制不能靠改文案消除；按现有说明提供服务端 cURL，不为了在线演示而扩大后端权限。

Sandbox 密钥只保留在当前页面会话内存中。不得加入 `localStorage`、`sessionStorage`、URL、遥测、日志或仓库；示例只使用合成数据。组件卸载或导航后仍在执行的写入不能被描述成“已取消”。

## C06 — 资金语义与失败恢复

- HTTP 成功、API 业务成功、请求受理、处理中和资金终态分开解释。查询成功也不证明付款完成。
- 状态说明使用四列：**状态值 / 含义 / 能证明什么 / 不能证明什么及下一步**。不能给未知状态自行命名或添加终态。
- 超时、网络断开或 5xx 可能发生在写入之后；写明该接口的查询与恢复方法。只有契约明确支持时才能用同一幂等键重放，不能默认重新创建。
- 金额保持原契约的类型、精度、单位和币种；示例不使用二进制浮点计算金融金额。
- 区分总额、可用、冻结与其他余额口径；区分退款、撤销、冲正和 MED；不以交易列表求和替代对账或余额。
- 回调按原始请求体验签，说明防重放、去重、乱序、确认与恢复。ACK、重试次数或时间只能写已确认值。

所有接口必须单独确认成功和错误的判断方法。已有接口的 HTTP/业务码包装不能未经核实复制到新增接口。

## C07 — 页面与代码示例

MDX `title`、`sidebarTitle`、`description` 必须清晰且与页面用途一致；正文从 H2 开始。第一段用纯文字说明能完成什么；前置条件放在第一项动作之前，不能藏在折叠区域。

OpenAPI 生成参数和响应参考；正文负责凭证范围、业务前提、状态意义、异常恢复与相关操作。避免用 `ParamField` 手工维护第二份完整字段定义。

六种语言的 `x-codeSamples` 必须对应同一个操作与业务请求，不凭空生成 SDK。每次新增接口都检查路径、签名、请求体字节、响应解析、超时与重试处理；能运行的示例才标为已测试。

新增 Webhook 使用 spec 的 `webhooks` 绑定，并复用已确认的回调处理规则；不要给接收回调的页面添加发送业务请求的签名器。

## C08 — 品牌和视觉基线

| 项目 | 当前契约 |
| --- | --- |
| 对外身份 | Pagsmile 巴西业务品牌；不把业务地域写成未经核实的集团起源或资质 |
| Mintlify 主题 | `almond` |
| 主色与强调色 | 主色 `#0E2A4B`；薄荷绿 `#2BC196`；复用现有 `--pgs-*` 变量 |
| 字体 | 标题 Space Grotesk，正文 Geist |
| 首页 | 简洁起步任务、关键操作入口和产品分组优先 |
| Hero | 桌面紧凑基线为 `min-height: 268px`；新增接口不扩大特效区域，不把重要入口推到更下面 |
| 品牌动效 | 完整 Logo 连续循环；有暂停/恢复；不恢复拼装或重播式演出 |
| 响应式 | 窄屏保持内容与操作可用；现有 ≤720px 隐藏 Hero 装饰动效 |

新增业务内容默认不修改 `style.css`、`layout.css`、`hero.css`、`snippets/connection-map.jsx`、logo、品牌图和全站主题。确有设计需求时把原因、影响范围和截图写入 PR；不能用一轮接口更新顺带重做配色、字体或首页。

## C09 — 组件与无障碍

优先使用已有 Mintlify 组件和 snippets。新增 CSS 使用局部 `pgs-` 类，避免无边界的 `body`、`button`、`a` 等覆盖；全站 CSS 文件会影响所有页面。

交互控件使用真实的 button、label 和输入字段，支持键盘、可见焦点、明确错误与恢复动作。明暗模式均应可读，不能只靠颜色区分状态。

动效必须支持减少动态偏好、暂停、离屏和后台降耗，以及加载失败时的静态回退；装饰不阻塞正文和 CTA。新依赖、浏览器 API 或第三方脚本要先确认 Mintlify 实际支持，不能把普通 React 项目的能力直接套到 MDX。

## C10 — 公开边界

仅提交审核过的 public spec；不上传完整内部服务定义、客户请求、密钥、日志、证件或账号信息。页面隐藏、从导航移除、`noindex` 都不是访问控制。

维护指南、模板和测试由 `.mintignore` 排除站点发布；这不是 GitHub 权限控制。证据中包含非公开信息时只在受控系统留存，并在公开 PR 中记录可公开的确认结论。

## C11 — 检查不能被静默绕过

新增接口同时覆盖 spec、页面、导航、两种语言和六语言示例；改变引用标识时检查 Arazzo。自动检查覆盖结构与已编码边界，人工审阅覆盖意义与实际行为。

不得因为新增接口使测试失败就删除断言、删掉示例语言或关闭 OpenAPI 校验。确实变更契约时，同一 PR 中说明依据、调整规则、补充验证，并让对应负责人确认。

## C12 — 发布要有结论

完成定义：事实已确认、双语内容齐全、适用审阅已完成、自动检查通过、读者路径可用、部署 commit 已确认、线上页面已核对、回退方式已记录。

“未测”“待翻译审阅”“仍在发布”是有效状态，但不能写成“已全部验证”。GitHub Actions 是否强制阻止合并由仓库保护设置决定；不能把 workflow 存在本身当成已强制执行。
