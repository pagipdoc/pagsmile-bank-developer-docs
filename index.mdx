## One call, end to end

A request carries four signature headers and a JSON body. JSON business responses use the same envelope: read `code` first, then `data`.

Handle HTTP 400 `text/plain` transport failures separately; do not parse them as JSON.

<Columns cols={2}>

```http Request
POST /v3/pix_keys/create HTTP/1.1
Host: ebanking-openapi-sandbox.pagsmile.com.br
Content-Type: application/json
User-Agent: your-app/1.0
X-Client-ID: <SANDBOX_AK>
X-Timestamp: 1791792000000
X-Nonce: 9f86d081884c7d659a2feaa0c55ad015
X-Signature: <64 lowercase hex characters>

{"pix_key_type":5}
```

```json Response (HTTP 200)
{
  "code": 200,
  "message": "success",
  "data": {
    "pix_key": "8e67c99a-7c55-4e91-9557-512b5e198561",
    "pix_key_type": 5,
    "status": 1,
    "created_at": 1791792000000
  },
  "time": 1791792000000
}
```

</Columns>

## Your first call in four steps

<Steps>
  <Step title="Get credentials and allowlist your IP">
    Each AK/SK pair has one credential type (`ACCOUNT`, `USER` or `PLATFORM`) and one environment. Requests from an IP address that is not on the credential's allowlist fail with `4004103`. See [Environments and credentials](/environments-and-credentials).
  </Step>
  <Step title="Sign the request">
    Send `X-Client-ID`, `X-Timestamp`, `X-Nonce` and `X-Signature` on every call. A timestamp more than 5 minutes off and a reused nonce are both rejected. See [Sign requests](/environments-and-credentials#sign-requests).
  </Step>
  <Step title="Read code, not the HTTP status">
    Every JSON business result, success or error, returns HTTP 200. When `code` is `200`, the request was accepted; any other value is described in the [error catalog](/api-reference/error-catalog).
  </Step>
  <Step title="Confirm the outcome">
    Use [webhooks](/api-reference/webhooks/overview) and the details endpoints to confirm the final status before you release goods or funds.
  </Step>
</Steps>

## Core terms

| Term | Meaning |
| --- | --- |
| <Tooltip tip="Master Account">MA</Tooltip> | Master account that establishes the party and the ownership of its managed accounts. |
| Managed account | An account created under an MA: MOR, VA or PA. |
| MOR | Operating account that reuses the approved compliance records of its parent MA. |
| VA | Managed account that belongs to a parent MA and has its own compliance records and bank account. |
| PA | Payment account that belongs to a parent MA, or to a VA under that MA, and has its own compliance records and bank account. |
| `PLATFORM`, `USER`, `ACCOUNT` | The three API credential types. They decide which accounts a call can act on. |
| <Tooltip tip="Identificador do Sistema de Pagamentos Brasileiro: the 8-digit code of an institution that participates in the Brazilian Payments System.">ISPB</Tooltip> | Institution identifier. Together with the account number, it identifies a bank account. |
| Pix key | Identifier that points to the account that receives a Pix. It is not an API credential. |
| End-to-end ID | ID of the original Pix transaction. Refunds and MED cases refer to it. |
| <Tooltip tip="Mecanismo Especial de Devolução: the Central Bank of Brazil's special return mechanism for Pix.">MED</Tooltip> | Pix special return mechanism, with its related infraction reports. |
