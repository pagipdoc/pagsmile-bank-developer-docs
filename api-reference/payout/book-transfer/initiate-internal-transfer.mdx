Submit a transfer between different internal accounts whose ISPBs match. A successful submission accepts the transfer for asynchronous processing, not completion.

| Credentials | Duplicate key | Result |
| --- | --- | --- |
| ACCOUNT, USER | `merchant_order_id` | Asynchronous |

## Before you call

<Tabs>
  <Tab title="ACCOUNT" icon="building-columns">
    Use the credential bound to the payer account. Omit both `X-ISPB` and `X-Account-Number`, or send both with values matching that account.
  </Tab>
  <Tab title="USER" icon="user">
    Send both `X-ISPB` and `X-Account-Number` for an account owned by the USER. These headers select the payer, not the payee.

    Include both headers in the [signature](/environments-and-credentials#sign-requests).
  </Tab>
  <Tab title="PLATFORM" icon="server">
    <Warning>PLATFORM credentials cannot call this endpoint. Use an ACCOUNT or USER credential for the payer account.</Warning>
  </Tab>
</Tabs>

The payer account must be enabled to send payments. Verify the payee's account and document details before submitting.

## Check the receiving account

The receiving account must exist, be active, be enabled to receive payments and have no closure in progress.

Its ISPB, account number, branch and account type must match your request. The document number and document type must match the account holder.

A payee ISPB different from the payer's returns `4001` with message `Invalid payee.bank_code value`.

Use a different account from the payer. This endpoint does not transfer to another institution; use [TED](/api-reference/payout/ted/initiate-ted-payment) for that route.

## Prepare the amount

Send the amount as a decimal string in BRL, such as `"10.00"`. It must be positive and exactly representable with two decimal places.

Applicable fees for both accounts are checked before acceptance. The amount must exceed the payee's total fee, so the credited amount remains positive.

Your configured payment limits also apply to internal transfers. A limit rejection returns business code `4001998`; this page does not specify a universal numeric limit.

## Read the result

All JSON business results return HTTP `200`. Read `code` before using `data`; only unreadable bodies or invalid JSON return HTTP `400` with plain text.

When `code` is `200`, save `data.txn_id` and the original `merchant_order_id`. Use the saved transaction ID to [query the transfer](/api-reference/payout/get-payment-status).

| Status | Meaning | What it proves | Next step |
| --- | --- | --- | --- |
| `5` PROCESSING | Accepted for processing | Submission only | Query the original transfer |
| `2` COMPLETED | Transfer completed | Confirmed completion | Reconcile the transfer |
| `3` FAILED | Transfer failed | Recorded failure | Review payment details |
| `4` CANCELLED | Transfer cancelled | Recorded cancellation | Review payment details |

Submission returns `5` (PROCESSING). Check the status or details with the same payer account context before treating the transfer as complete.

The submission response returns `null` for `payee`, `payer` and `error`. Retrieve participant information through [Get payment details](/api-reference/payout/get-payment-details).

## Retries and duplicates

Use an order ID unique across accounts and operations in the same environment. Accepted IDs remain reserved for up to 48 hours.

<AccordionGroup>
  <Accordion title="The submission result is unknown" icon="clock-rotate-left">
    After a timeout, network failure or system error, investigate the original transfer before resubmitting. An early query may not find the transaction yet.

    Query again rather than creating a new transfer. If you did not receive `txn_id`, retain the order ID and response header `xxx-log-id` for support.
  </Accordion>
  <Accordion title="The order ID is already reserved" icon="clone">
    A repeated request with a retained `merchant_order_id` returns `4001013` (Already processed). It does not replay the original success response.

    Changing the order ID can create another transfer. See [Payout overview](/api-reference/payout/overview) for handling an unknown result.
  </Accordion>
  <Accordion title="Signing failed" icon="signature">
    Sign each attempt with a new `X-Nonce` and `X-Timestamp`. The nonce is consumed even if the signature fails.

    See [authentication errors](/api-reference/error-catalog#authentication-errors).
  </Accordion>
</AccordionGroup>
