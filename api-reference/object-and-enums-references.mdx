Find the meaning of a field value across the Open API v3. Expand an enum to see its numeric mapping and the restrictions that apply to each endpoint.

<Note>
  Send JSON numbers for numeric fields, such as `"model": 2`. Callback fields can use [string enum names](#string-enum-fields). A shared enum can contain more values than an endpoint accepts; check the endpoint schema before sending a request.
</Note>

## JSON conventions

<AccordionGroup>
<Accordion title="JSON formats and timestamps">

| Data | JSON representation | Integration rule |
| --- | --- | --- |
| Numeric enums | `2` | Do not replace a number with a label such as `"ACTIVE"`, unless the field is explicitly a string. |
| Amounts, fees and balances | `"10.50"` | Use decimal strings and decimal arithmetic. Follow endpoint precision rules. |
| Account and document identifiers | `"00123456"` | Preserve leading zeros; do not parse identifiers as numbers. |
| Timestamps | Integer | `time` and explicitly documented millisecond fields use Unix milliseconds. Check the unit of each field. |
| Durations | Integer | Dynamic QR `expires` is seconds, not an epoch timestamp. |
| Missing or unpopulated data | `0`, `""`, `null` or an empty collection, depending on the field | Follow the field's schema. An unspecified enum is not a successful or final outcome. |

`updated_at` in managed-account and webhook-subscription responses can contain Unix seconds or milliseconds. `0` means unavailable; a nonzero value below `1000000000000` is seconds. Managed-account `activated_at` records compliance approval time, not proof of bank-account activation.

</Accordion>

<Accordion title="Shared object shapes">

These are common field groups. The linked endpoint documents the complete shape, nullability and field behavior.

| Object | Common fields | Reference |
| --- | --- | --- |
| Bank account reference | String `ispb` and `account_number` | [Managed account details](/api-reference/onboarding/get-managed-account) |
| Transaction party | `name`, `document_id`, numeric `document_type`, bank identifiers and numeric `bank_account_type` | [Account statement](/api-reference/accounts/get-account-statement) |
| Transaction details | Parties, IDs, numeric `txn_status` and `source_type`, decimal-string amounts and fees, timestamps and payment details | [Payment details](/api-reference/payout/get-payment-details) |
| Statement entry | Transaction IDs, `amount`, `is_credit`, parties, numeric type/status/method/variant and parent IDs | [Account statement](/api-reference/accounts/get-account-statement) |
| Account and balances | Identifiers, balances, `pix_keys`, `limit_config`, `webhooks` and `fee_configs` | [Account balance](/api-reference/accounts/get-account-balance) |
| Managed account | `reference_id`, model, account and compliance statuses, holder data, lifecycle times, `account` and `linked_account` | [Managed account details](/api-reference/onboarding/get-managed-account) |
| Webhook subscription | `webhook_id`, string `event_type`, `callback_url`, numeric `status`, lifecycle times and subscription identifiers | [Subscription details](/api-reference/webhooks/get-event-subscription) |
| Page metadata | `page`, `page_size`, `total` and `total_pages` | [List managed accounts](/api-reference/onboarding/list-managed-accounts) |
| Statement cursor | Integer `timestamp`, string `id` and numeric `direction` | [Account statement](/api-reference/accounts/get-account-statement) |
| MED case | IDs, numeric status, decimal-string amounts, deadlines, original transaction, timeline and linked infraction/return summaries | [MED case details](/api-reference/med/get-med-case-details) |

Do not interchange page-number pagination with statement cursors. A managed account's `account` can be `null` until both bank identifiers are available; `linked_account` is the PA's parent account and is `null` for MOR and VA.

</Accordion>
</AccordionGroup>

## Accounts and identity

Use these definitions with [managed accounts](/api-reference/onboarding/get-managed-account) and [transaction parties](/api-reference/accounts/get-account-statement). Account status and compliance status describe separate stages.

<AccordionGroup>

<Accordion title="Document type · document_type">

| Value | Name |
| --- | --- |
| `0` | `UNSPECIFIED` |
| `1` | `CPF` |
| `2` | `CNPJ` |

Numeric in transaction parties and onboarding requests. CPF identifies an individual; CNPJ identifies a company. Onboarding requests accept only `1` or `2`. Managed-account query responses return document type as a string.

</Accordion>

<Accordion title="Bank account type · bank_account_type">

| Value | Name |
| --- | --- |
| `0` | `UNSPECIFIED` |
| `1` | `CHECKING` |
| `2` | `SALARY` |
| `3` | `SAVINGS` |
| `4` | `PAYMENT` |
| `5` | `TRANSCTIONAL_PI` |
| `6` | `GUARANTEED` |
| `7` | `DEPOSIT` |

Bank-detail payout requests accept only `1`–`4`. The additional values belong to the response contract. Preserve the published spelling `TRANSCTIONAL_PI` when reading named callback values.

</Accordion>

<Accordion title="Managed account model · model">

| Value | Name |
| --- | --- |
| `0` | `UNSPECIFIED` |
| `1` | `MOR` |
| `2` | `VA` |
| `3` | `PA` |

Creation requests select `1`, `2` or `3`. Each model has its own required fields. See [Create managed account](/api-reference/onboarding/create-managed-account).

</Accordion>

<Accordion title="Managed account status · status">

| Value | Name |
| --- | --- |
| `0` | `UNSPECIFIED` |
| `1` | `PENDING` |
| `2` | `ACTIVE` |
| `3` | `FROZEN` |
| `4` | `CLOSED` |
| `5` | `REJECTED` |
| `6` | `EXPIRED` |
| `7` | `PENDING_SUBMISSION` |

Get and list do not currently emit `7`; unmapped statuses return `0`. The create response maps `0`–`6`. Pending applicant submission is represented by `compliance_status = 2`. Confirm `status = 2` and the returned bank account before treating an account as active.

</Accordion>

<Accordion title="Compliance mode · compliance_mode">

| Value | Name |
| --- | --- |
| `1` | `HOSTED_LINK` |
| `2` | `API_BODY` |
| `3` | `PROVIDER_SESSION` |

`1` returns a hosted verification link; `2` submits a KYC/KYB payload; `3` uses provider-session information. Omit this field for MOR.

</Accordion>

<Accordion title="Compliance status · compliance_status">

| Value | Name |
| --- | --- |
| `0` | `UNSPECIFIED` |
| `1` | `PENDING` |
| `2` | `PENDING_SUBMISSION` |
| `3` | `APPROVED` |
| `4` | `REJECTED` |
| `5` | `EXPIRED` |
| `6` | `CREATION_FAILED` |
| `7` | `REVIEWING` |
| `8` | `ERROR` |
| `9` | `FORCE_APPROVED` |

Queries use numbers. KYB callbacks use these names as strings, without a `COMPLIANCE_STATUS_` prefix, and do not include `UNSPECIFIED`. `APPROVED` or `FORCE_APPROVED` alone does not prove account activation.

</Accordion>

</AccordionGroup>

Creation requests accept `1`–`5`. Static QR generation accepts only `5` (a random EVP key).

## Transactions and statements

Read the enum in the context of its endpoint. [Payment status](/api-reference/payout/get-payment-status), [payment details](/api-reference/payout/get-payment-details) and [refund status](/api-reference/refunds/get-refund-status) expose different subsets.

<AccordionGroup>

<Accordion title="Transaction status · txn_status">

| Value | Name |
| --- | --- |
| `0` | `UNSPECIFIED` |
| `1` | `PENDING` |
| `2` | `COMPLETED` |
| `3` | `FAILED` |
| `4` | `CANCELLED` |
| `5` | `PROCESSING` |
| `6` | `REFUNDED` |
| `7` | `PARTIALLY_REFUNDED` |
| `8` | `DISPUTED` |

The payment-status endpoint returns `0`–`5`; `2`, `3` and `4` are final payment statuses. Details and statements can include display statuses `6`–`8`. Refund status uses `0`, `1`, `2`, `3`, `5`; a completed partial refund is also `2`. A recipient-side refund-status query returns `5` for every non-completed refund, including failures.

</Accordion>

<Accordion title="Transaction type · txn_type">

| Value | Name |
| --- | --- |
| `0` | `UNSPECIFIED` |
| `1` | `PAYMENT` |
| `2` | `REFUND` |
| `3` | `TRANSFER` |
| `4` | `WITHDRAWAL` |
| `5` | `DEPOSIT` |
| `6` | `DISPUTE` |

The statement query returns PAYMENT, REFUND and DISPUTE entries. Its request field is `transaction_type`, which accepts only `0`, `1`, `2` and `6`. Other shared enum values are rejected as filters.

</Accordion>

| Value | Name |
| --- | --- |

| `1` | `APP` |
| `2` | `API` |
| `3` | `SCHEDULE` |
| `4` | `BATCH` |

QR-code transaction details and refund details currently leave this field at `0`, including for API-initiated refunds. Do not infer the origin from an unpopulated value.

<Accordion title="Funds direction · funds_type">

| Value | Name |
| --- | --- |
| `0` | `UNSPECIFIED` |
| `1` | `CREDIT` |
| `2` | `DEBIT` |

Statement filter. `0` selects both directions, `1` selects credits to the target account, and `2` selects debits from it. The entry itself uses the boolean `is_credit`.

</Accordion>

<Accordion title="Cursor direction · direction">

| Value | Name |
| --- | --- |
| `0` | `UNSPECIFIED` |
| `1` | `FORWARD` |
| `2` | `BACKWARD` |

The statement response supplies direction `1` for the next page. Reuse the returned cursor and `snapshot_timestamp`. `0` defaults to forward pagination; only `2` requests backward pagination.

</Accordion>

</AccordionGroup>

## String enum fields

Keep these fields as strings. Do not apply the numeric tables above to callback payloads or fee configuration objects.

| Context | Field | Representation |
| --- | --- | --- |
| Managed-account queries | `document_type` | `"CPF"`, `"CNPJ"`, or `""` when unavailable. |
| KYB callbacks | `event_type` | `"VA_ACCOUNT_KYB"`. |
| KYB callbacks | `subject_type` | `"VA_MOR"` for MOR, `"VA"` for VA, `"PA"` for PA. |
| KYB callbacks | `status` | A compliance name such as `"APPROVED"`; see the compliance-status table. |
| Transaction callbacks | Status, type, method, variant and party enum fields | Full enum names, such as `"TXN_STATUS_COMPLETED"`, `"PAYMENT_METHOD_PIX"`, `"DOCUMENT_TYPE_CNPJ"` or `"BANK_ACCOUNT_TYPE_PAYMENT"`. Accepted names depend on the event schema. |
| Transaction callbacks | `flow_type` | `"FLOW_TYPE_IN"`, `"FLOW_TYPE_OUT"` or `"FLOW_TYPE_TRANSFER"`, depending on the event. |
| Account balance `fee_configs` | Every field, including `fee_kind` | Strings; `charge_type` is `"PERCENTAGE"` or `"FIXED"`. |
| MED objects | `status_display`, `freeze_status` | Descriptive strings; use the adjacent numeric status for decisions. |

<Accordion title="KYB result codes · result_code">

`result_code` is independent of callback `status`. Empty or unsupported codes become `"UNKNOWN"`. `READY_FOR_REVIEW` and `RESUBMIT_REQUIRED` are result codes, not status values.

| String value |
| --- |
| `"PENDING"` |
| `"PENDING_SUBMISSION"` |
| `"REVIEWING"` |
| `"READY_FOR_REVIEW"` |
| `"APPROVED"` |
| `"REJECTED"` |
| `"EXPIRED"` |
| `"ERROR"` |
| `"UNKNOWN"` |
| `"FORCE_APPROVED"` |
| `"RESUBMIT_REQUIRED"` |
| `"CREATION_FAILED"` |

</Accordion>

For complete event payloads, see [KYB callbacks](/api-reference/onboarding/kyb-callbacks) and [transaction callbacks](/api-reference/webhooks/transaction-callbacks). The TED request field `purpose` is currently ignored; omit it rather than using a legacy purpose enum.
